## Risk review

For each system overview, review the following questions against the actual change. Return the material findings in overview.risks. Each finding names the affected file and symbol in evidence, describes the trigger and consequence in scenario, and gives a specific check or reproduction in verify. Link stopId to the relevant walkthrough stop where possible. Distinguish a demonstrated defect from a question whose answer requires production data. Account for existing safeguards. Never invent traffic, row counts or missing behavior from a truncated excerpt. Return an empty array when the available evidence yields no specific finding.

- **Behavior removed or consolidated.** Trace the old job to its new owner. Check callers, side effects, permissions, error paths, cleanup, platform exceptions and assertions that disappeared. If the rationale or replacement is unclear, identify the exact old behavior to verify.
- **Work multiplied by traffic or data.** Count queries, writes, network calls and queued jobs per request, row and retry. Explain what multiplies at thousands of requests. Check indexes, pagination, batch size, memory, timeouts and queue capacity. Distinguish synchronous API work from asynchronous work that can still overwhelm the same dependency.
- **Migrations and backfills.** Establish production cardinality, expected writes, lock scope, mixed-version compatibility and deployment order. Check resumable progress, bounded transactions, partial completion and verification before tightening constraints.
- **Async correctness and recovery.** Follow commit, enqueue, retry, cancellation and acknowledgement boundaries. Check duplicate or stale work, overlapping workers, retry amplification and what an operator can observe or safely replay.
- **Frontend behavior and scope.** Trace shared components outside feature flags, cached and stale responses, query variables, in-place mutation, lifecycle cleanup and out-of-order requests. Check large lists, repeated renders, requests per interaction, keyboard behavior and supported input methods when relevant.
- **Proof of behavior.** Check whether realistic fixtures distinguish the old and new paths. Ask what assertion would fail for the specific regression, including existing records, empty states, failures and rollout boundaries.
